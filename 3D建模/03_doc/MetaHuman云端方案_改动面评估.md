# 若改用 UE5 MetaHuman 做云端数字人 —— 改动面评估

> 用途：给"是否从端侧方案（uni-app + three.js + 自建 GLB）转向 UE5 MetaHuman 云端方案"提供可拍板的依据。
> 状态：**评估中**（调研员正在核实 MetaHuman 现行形态、授权、国内 GPU 与 RTC 价格，结果将补入 §2/§6/§7）
> 基线（当前方案的事实，均为实测）：端侧渲染；`uni-app/static/avatar/*.glb` 四件；
> 编辑期 60k 三角面 / 33 骨 / 113 `shape_*`；运行期 7 骨 / `vis_* 15 + expr_* 8`；
> 交付契约上限：**三角面 ≤60k、贴图 ≤2K、GLB ≤8MB、骨数 ≤70**（`比邻AI_数字人资产交付规范.md` §5）

---

## 0. 一句话结论（先给判断）

**结论：技术上做得到，但"实时面部驱动"这一环在 Linux 云端跑不了，成本结构又与康养场景冲突；
授权不是阻碍（2025-06 已放开），真正的硬约束是技术与合规。建议维持端侧方案。**

四条决定性依据（均有来源，见对应章节）：

1. **授权不是阻碍**（`2025-06` 起）：MetaHuman 工具集已由标准 UE EULA 覆盖，可商用、
   可用于任何引擎、可出售；像素流输出属 "streamed video files"（Non-Engine Products），
   **不产生 UE 5% 分成**；唯一例外是**不得用于训练/增强 AI 模型**。（§8.2）
2. **⚠️ 技术硬约束：MetaHuman Animator 官方不支持 Linux/macOS**
   （官方原文 "MetaHuman Animator is currently not supported on macOS and Linux."）。
   云端 GPU 实例几乎都是 Linux；Animator 的 Linux 支持仍是 "planned for a future release"。
   → **"云端实时面部驱动"这条链在 Linux 服务器上直接断掉。**（§3）
3. **成本与并发结构不成立**：Pixel Streaming 默认 **1 路并发 = 1 个 UE 实例**
   （Epic 工程师原话）；单卡硬编并发上限 **8（Epic 文档）/ 12（NVIDIA 官方）** 且两者口径冲突；
   单角色 Cinematic **1–2 GB 显存**、Groom **约 16 MB/角色且全量常驻、无流式卸载**；
   每路有现成报价 **¥1–8/路/小时**（腾讯云 CAR 包月折合 ¥0.73–1.33/路/小时，
   天翼云 ¥2.5–7.8/路/小时）；**冷启动 1.5–3 分钟**。（§5/§7）
4. **合规上，端侧处理是"主路径"而非取舍**：《人脸识别技术应用安全管理办法》第八条
   ——**人脸信息默认应当存储于设备内、不得通过互联网对外传输**（仅"法定例外或单独同意"两条例外），
   第五条还**专门点名老年人**；另有 PIPL 生物识别敏感个人信息、影响评估留存 3 年、
   10 万人备案等义务。**我们现在的做法（真实面部从不出手机、只上传参数）恰好落在安全侧。**（§8.1）

**另一个降低决策风险的发现**：视觉模式（`pages/vision`）**目前是零实现**
（页面是 CSS 画的占位人形；端侧 API 与服务端都没有 vision 模块）。
所以这不是"推翻已有系统"，而是"决定第一版怎么做"。

**建议**：维持端侧（方案 §472 的既定判断在技术、成本、合规三条上同时被支持）；
若仍想验证，**先做 §10 的"阶段 0"抽象**（把形象来源抽成 provider，无论哪条路都该做），
**并把合规问询（问网信/法务：表情驱动、非身份识别是否落入办法第八条）放在技术投入之前**。

## 1. 架构层面的改变（必然发生）

| 维度 | 现在 | 换 MetaHuman 云端后 |
|---|---|---|
| 渲染位置 | 手机本地 WebGL（three.js / renderjs） | 云端 UE5 实例（Linux + headless） |
| 资产格式 | `.glb`（Blender 导出，自建 33/7 骨） | UE 的 `.uasset` / MetaHuman 资产包（体积与结构完全不同） |
| 资产管线 | 我们自建的 Blender 无头管线（已有 20+ 工具、全套审计） | UnrealEditor-Cmd + MetaHuman 管线（**现有 Blender 管线对本方案无用**） |
| 端侧职责 | 渲染 + 应用 morph 权重 | **只做解码播放 + 收音频**（渲染权重全部移到云端） |
| 传输 | 逻辑层 → 端侧渲染器（同进程调用，0 延迟） | 端侧 ↔ 云端：WebRTC（信令 + 媒体）+ 控制通道 |
| 服务器 | 现在无 GPU 依赖（mock-server / agent 服务） | 新增 **GPU 渲染集群 + 信令服务 + RTC 转推** |
| 降级路径 | 三重降级（降帧 → 口型降级 → 静态形象） | 要多一条"云端不可用 → 回退端侧 GLB"或"纯语音" |

**关键结构性差异**：现在 `pages/face` 与通话页**共用同一份 `.glb` 与同一套参数**
（方案 §483），换成云端后这条"一份资产两处用"的链路会断——云端是 UE 资产，
端侧是 GLB，**要么维护两份形象、要么捏脸也上云**。

| 项 | 当前 GLB（编辑期） | MetaHuman LOD0 | 倍数 |

- **注意**：MetaHuman 的 669 个 blendshape 与我们的 `shape_*`（捏脸）+ `vis_*`（口型）
  是两套命名体系，**捏脸参数体系要重新映射**（见 §3）。

## 3. 口型/表情驱动链路的改变（**最容易被低估的一块**）

现在（已落地）：`TTS 音频 → 字级强制对齐 → viseme 曲线 → 端侧写 vis_* morph`，
方案 §340/§362 定义 15 个 viseme 组，`/v1/vision/session`（WS）把曲线下发端侧。

MetaHuman 网络方案下，这条链路要整体重做，而且存在一个**先天的平台断点**：

**⚠️⚠️ 最硬的一条：MetaHuman Animator 官方不支持 Linux/macOS。**
官方原文：**"MetaHuman Animator is currently not supported on macOS and Linux."**
平台限制表另注明「Realtime Animation from mono video or audio: **only supported on Windows and macOS**」、
Markerless Mocap 插件**仅 Windows**；5.7 才刚把 MetaHuman Creator 搬上 Linux，
**Animator 的 Linux 支持仍是 "planned for a future release"**。
→ 而云端 GPU 渲染实例（阿里云/腾讯云/AWS 的 GPU 机型）**几乎全是 Linux**。
**这意味着"云端实时面部驱动"这条链在 Linux 服务器上跑不起来**——不是调优问题，是官方未支持。

其余要重做的部分：
- MetaHuman **不吃我们的 `vis_*`**，它走 ARKit Face 风格 blendshape 或官方音频驱动方案
  （Live Link Face / MetaHuman Animator 离线解算 / 官方 Audio Driven Animation /
  `Use ARKit Face` 开关；注意**"ARKit 52"这个计数在官方文档里并未出现**，官方只说"ARKit Face"）；
- 于是要么 **① 在服务端把 viseme 曲线重映射成 ARKit 风格**，要么
  **② 改走"音频直驱"**（把 TTS 音频送进云端由 UE 侧做音频驱动口型）；
- ②更省事，但把口型质量交给 UE 侧方案，且**每个会话都要推音频上行**（带宽/合规）；
- 我们已建的 `morph-viseme-cosyvoice2.json`（jaw 角度标定）等标定**全部作废**，要在 MetaHuman 上重标；
- 方案 §370 的"捏脸 morph 与口型 morph 分属两个命名空间"这条经验，
  在 MetaHuman 上由它自己的 **Rig Logic** 接管，**我们的两层分离设计不再适用**；
- **NVIDIA Audio2Face → MetaHuman 未见官方集成文档**，且 Audio2Face-3D 标 `license: other`，
  **商用条款未找到权威结论** → 不要把口型方案押在它上面。

## 4. 产品体验上会破掉的两件事（与下一节同源）

1. **捏脸的即时手感**（方案 §472 的判据）：拖滑杆→云端往返 200~500ms/帧，手感必然崩。
   → 要么**捏脸仍走端侧 GLB**（那就得维护两份形象，且两边要长得像），
   要么**改成"选预设 + 异步生成"**（牺牲产品定义的核心体验）。
2. **低端机/弱网可用性**：现在有"首启能力探测 + 三重降级"；云端方案下，
   网络一抖就是画面卡顿/掉线，对**老人**是明显的体验与信任损伤，
   而且我们的"一键停止"红线要在流层面再实现一遍。

## 5. 延迟预算（**会直接撞上产品自己的指标**）

方案 §333 给视觉模式定的端到端预算是：**viseme 生成 + 渲染上屏 ≤ 100ms**。
云端方案要把这条链路拆成"上行/编码/网络/解码"四段额外开销：

| 环节 | 端侧（现在） | 云端（MetaHuman 方案） |
|---|---|---|
| 渲染 | 手机本地，同进程调用 | 云端 UE 渲染（+ 编码 H.264/AV1） |
| 画面传输 | **无** | 云端 → 端侧：网络 RTT + 编解码 + 抖动缓冲 |
| 口型驱动 | 服务端下发 viseme，端侧写 morph（同进程） | 需在云端生效（推音频或推 blendshape），**多一次上行** |
| 端到端典型量级 | 目标 ≤100ms（方案 §333） | **Pixel Streaming 的官方参考建议在局域网/专线做实测标定**（[Epic 官方 Pixel Streaming 参考](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-pixel-streaming-reference)），公网同城通常在**上百毫秒量级**，跨省更差 |

**这条对产品的实际含义**：
- "跟数字人对话"是**实时交互**场景，延迟每增加一档，老人感受到的是"她反应慢/卡住了"；
- 端侧方案的 100ms 预算在云端方案下**基本不可能保住**；
- 而这恰好是**康养场景最敏感的地方**（老人对"对面是不是活的"的判断更依赖即时反馈）。

> 诚实标注：我**没有**拿到"国内公网 Pixel Streaming 端到端延迟"的权威实测数字，
> 上面给的是量级判断。这个数字必须在阶段 1 用真实机型 + 真实网络**实测**，
> 而不是照抄任何厂商宣传值。

## 6. 需要新增的工程件（粗略清单）

- 云端：UE Linux 打包、headless 启动、MetaHuman 资产加载、多实例管理、健康检查、优雅回收
- 信令与媒体：Pixel Streaming 信令（或第三方 RTC）、TURN/STUN、码率自适应
- 端侧：`<video>` / RTC SDK 播放器、与现有 `pages/call` 的对接、延迟与断线处理
- 控制面：会话编排（谁在哪个实例）、排队与限流、监控与告警、成本看板
- 账号与安全：实例隔离（不同老人的会话不能串）、鉴权、录制与留存策略（如有）
- 回退：云端不可用时切回端侧 GLB 或纯语音 + 静态形象

## 7. 成本结构（**已有权威单价与现成报价，可算出量级**）

### 7.1 单价来源

**通用云渲染按量**（[阿里云 GCS 官方计费页](https://help.aliyun.com/zh/gcs/product-overview/billing-overview)）：
7.059 ~ 34.406 元/时（按 R 实例规格）。

**"按并发路数"销售的现成报价**（比自建实例更贴近真实采购）：

| 供应商 | 每路价格 | 备注 |
|---|---|---|
| 腾讯云 CAR | 包月 S **1,717** / M **2,620** / L **3,765** / XL **4,775** 元/月（折合约 **¥0.73–1.33/路/小时**） | **只有预付费、无按量**；官方明说超并发要**排队等待并发释放** |
| 天翼云实时云渲染 | **¥2.5 / 6.4 / 7.8 元/路/小时**（标准/高级/旗舰） | 官方原文「1 路渲染实例同一时刻最多可为 1 个终端提供应用接入」 |
| 阿里云 GCS | 7.059 ~ 34.406 元/时（R 实例） | 按 R 实例规格 |

**裸 GPU 实例（对照）**：腾讯云边缘计算机器 T4 渲染型 GN7vw 16 核 64G / 1×T4 = **3,528 元/月**。

### 7.2 并发密度（决定成本能否摊薄）

- Epic 支持工程师官方论坛口径：**"我见过单机跑 4 个实例，但按我的经验大多数人最终是
  1 台机器跑 1 个 UE 实例"**（[来源](https://unreal2.epic-prod-us2.discourse.cloud/t/best-setup-for-running-multiple-avatars-with-pixel-streaming-50-500-users/2636562)）；
- 单卡硬编并发上限**两个口径冲突**：Epic 文档 **8**（第 9 路起自动切软编），
  NVIDIA 官方矩阵为消费级 GeForce 全系 **12**、专业/服务器卡不限 → **必须实测**；
- **显存是真瓶颈**：单角色 Cinematic 官方 **1–2 GB**；**Groom 约 16 MB/角色且全量常驻、
  无流式卸载**（Epic 工程师确认「no plan for cards to have streaming pool」，
  且「no crowd code, no ETA」）→ **不能简单用显存除以单角色占用**。

**带宽不是瓶颈**：1080p30 按 6 Mbps/路算，200 Mbps 出网 ≈ 33 路（阿里云固定公网 IP 出网峰值一般 ≤200 Mbit/s）。
**瓶颈在 GPU 渲染 + NVENC 编码**。

### 7.3 量级估算

| 假设 | 数值 |
|---|---|
| 按并发路数采购（腾讯云 CAR L） | 3,765 元/路/月 |
| 单次通话 | 8 分钟 |
| **单次通话算力成本** | **≈0.7–1.2 元**（视档位） |

**规模化后的账单量级**（只算渲染，不含 RTC 分钟费/带宽）：
**1 万活跃老人、晚高峰 10% 同时在线 = 1,000 路 × CAR L 包月 3,765 元 ≈ 376.5 万元/月。**

**结构性结论（与 §0 一致）**：
- **端侧方案的边际成本 ≈ 0**（用老人自己的手机），与装机量解耦；
- **云端成本 = 并发路数 × 单价 × 时长，严格线性**，且**短会话无法摊薄**
  （按路/月或小时包卖）、**峰值决定账单**、**超并发要排队**；
- 康养场景"用户量大 + 单次短 + 高峰集中"正是云端最吃亏的画像。
  **规模小（试点 10~50 路）时云端反而省事**，这也是 §10 阶段 1 只做小规模灰度的原因。

### 7.4 冷启动与可用性代价

- UE 应用启动 **1.5–3 分钟**（实测 OCI 90s / Azure 180s；Epic 支持定位为磁盘 IO；
  Azure 侧还在从远程 DDC 取贴图）→ 要压到秒级只能**预分配常驻**，代价是 **GPU 24/7 空转**；
- **⚠️ 抢占式/竞价实例不能用于实时服务**：阿里云抢占式在出价不足/库存不足时**5 分钟后释放**；
  腾讯云竞价虽"不因价格中断、只因库存不足中断"，但回收前 5 分钟通知、**数据不保留**，
  且官方明确**"不适用：没有采用负载均衡的在线服务"**。

### 7.5 小程序端的额外门槛（老人端主入口之一）

微信小程序 `<live-player>` 的 `src` **只支持 flv / rtmp，不支持 WebRTC**
（可用 `mode="RTC"` 降延迟）；live-player **仅对特定类目开放**，
需**类目审核 + 当地互联网主管机关审核（约 7 天）**、企业主体、
域名须 **https/wss 白名单 + ICP 备案**；**不支持个人小程序**。
康养可落类目为**「医疗-互联网医院 / 公立医疗机构 / 三级私立 / 其他私立」**。

## 8. 调研结论（合规 / 授权 / 价格）

### 8.0 ⚠️ 新发现：数字人已是**受专门监管的品类**（本轮最重要的合规增量）

《**数字虚拟人信息服务管理办法（征求意见稿）**》——国家网信办 **2026-04-03** 发布
（意见截止 2026-05-06，**施行日期尚空白**）。与我们直接相关的条款：

| 条款 | 内容 | 对产品的强制约束 |
|---|---|---|
| **第二十五条** | 定义「**真人驱动数字虚拟人 = 通过动作捕捉技术实时映射真人表情、动作和语音**」 | **我们的形态正好命中** |
| **第十三条** | **全程持续显示**含有「数字人」字样的**显著提示标识** | UI 硬约束：**常驻角标**，不能只弹一次 |
| **第十条** | 不得向未成年人提供**虚拟亲属、虚拟伴侣**等虚拟亲密关系 | 与伦理红线「不模拟已故亲属」同源；**产品叙事必须与"虚拟亲属"严格切割**（不叫"闺女""老伴"） |
| **第八条** | **未经特定自然人同意，不得提供足以识别特定自然人身份的数字虚拟人服务**（含"使用与特定自然人**高度相似的肖像或者声音**"） | 定制"像某位家人"的形象/声音，**须取得该自然人同意**（不是老人同意就够） |
| **第七条** | 用敏感个人信息建模须**单独同意**；**撤回同意后须删除并注销数字人** | 影响捏脸数据的存储与删除流程 |
| **第二十一条** | 具舆论属性/社会动员能力的须**算法备案**，**技术支持者参照执行** | 云渲染技术供应商也被纳入监管 |
| **第二十四条** | 罚则含「涉及危害公民生命健康安全且有危害后果的」罚 **10 万–20 万元** | 康养场景需格外注意 |

官方解读明确四类主体：**技术支持者 / 服务提供者 / 服务使用者 / 传播平台**，
且「**服务使用者需承担与服务提供者相同的责任义务**」。

**资质方面两个澄清（省掉不必要的工作）**：
- **文网文（网络文化经营许可证）不需要**：办市发〔2019〕81 号明确
  **聊天类等直播不属于网络表演**，不在审批范围（贵州省文旅厅 2026-01 红头文件亦确认）；
- **增值电信业务经营许可证通常也不需要**：广东省通管局明确「依托微信/支付宝等平台的
  **小程序、公众号、视频号、H5 网站、线上店铺**等形式经营，且无其他独立运营平台的，**无需取得**」；
- 但**《信息网络传播视听节目许可证》民营不可得**（须国有独资/控股）→
  自建独立视频服务是实质障碍，走云厂商/RTC 才可行。

### 8.1 人脸合规（**本方案最硬的一道墙，对养老产品尤其敏感**）

依据《人脸识别技术应用安全管理办法》（网信办、公安部令第 19 号，**2025-06-01 施行**）
——原文：[中国政府网](https://www.gov.cn/zhengce/zhengceku/202503/content_7016075.htm)：

| 条款 | 内容 | 对本方案的影响 |
|---|---|---|
| **第八条** | **除法律、行政法规另有规定或者取得个人单独同意外，人脸信息应当存储于人脸识别设备内，不得通过互联网对外传输** | ⚠️ **最关键**：默认禁止上云，**仅两条例外** |
| 第五条末 | **处理残疾人、老年人人脸信息的，还应当符合国家有关无障碍环境建设的规定** | 老人场景**额外**要满足无障碍要求（是合规项，不是产品偏好） |
| 第六条 | 须**单独同意**，并提供便捷的撤回方式 | 不能用"总隐私政策"打包同意 |
| 第九条 | 事前做**个人信息保护影响评估**并记录，报告**至少保存 3 年** | 新增法务/合规工作量 |
| 第十五条 | 存储数量达 **10 万人**之日起 30 个工作日内向省级以上网信部门**备案** | 规模化后新增义务 |

**一个对我们有利的边界**（第十九条(三) 把"人脸识别技术"限定为
「**以人脸信息作为识别个体身份**」的技术；第二条排除研发/算法训练场景）：
我们做的是**表情驱动/形象定制，不是身份识别**，严格文义上**未必**落入本办法。
**但这不等于安全**：① 人脸信息仍是《个保法》第 28 条的**敏感个人信息**
（与"医疗健康"同列，康养健康档案是双重敏感），第 29 条单独同意、第 55 条事前影响评估、
第 56 条报告留存 3 年**100% 适用**；② 第八条主语是"人脸信息"而非"识别用途"，
**存在被适用于云上传的显著风险**；③ 第五条**专门点名老年人**。
→ 这是**分析结论，不是官方定性**，正式立项前应做合规问询。

**产品级建议（与现有伦理红线同源）**：
- **尽量不上传真实面部**：捏脸走端侧（现在的做法）本身就规避了这条风险——
  老人的真实面部**从未离开手机**，上传的只是"参数"；
- 若要云端化，**优先只上传参数/预设，不上传照片或人脸网格**；
- 需要"像本人"时，**端侧拟合、只传结果参数**，而不是把面部数据送云端。

## 9. 代码改动面（已对照仓库实际文件，**比想象中小很多**）

**先说一个决定性的事实：视觉模式目前是零实现。**

| 事实 | 证据 |
|---|---|
| 通话/视觉页的数字人是 **CSS 画的占位图形**（两个圆角块），没有 canvas、没有 3D 引擎 | `uni-app/pages/vision/vision.vue`（5KB，`.bl-vision__head` / `__torso`） |
| **没有 vision/viseme 会话的端侧 API** | `uni-app/api/config.js` 只登记了 chat / plan / elders / reminder / push / memory，**无 vision** |
| 服务端没有 vision 相关模块 | `server/app/**` 无 vision/avatar/stream 文件；`tools/mock-server.mjs` 也无 |
| 捏脸页是唯一真在跑 3D 的地方 | `uni-app/pages/face/face.vue`（23KB）+ `common/face-gl/face-three.js`（26KB） |

**含义（重要）**：P3「视觉模式」还没开始建。所以"换云端方案"**不是在改一套已有系统，
而是在决定第一版怎么做**——这比"推倒重来"便宜得多。选择成本主要落在**要做的东西本身**，
而不是沉没成本上。反过来说，已经建好的资产与工具链（Blender 管线、四件 GLB、
契约判据、H5 复验手段）若不走端侧路线，就成了纯沉没成本。

| 文件 | 现状 | 云端方案要做什么 |
|---|---|---|
| `uni-app/pages/vision/vision.vue` | CSS 占位人形 | **新增**：RTC/视频播放器 + 连接状态 + 降级（或保持占位人形作为降级档） |
| `uni-app/api/config.js` + 契约文档 | 无 vision 端点 | **新增**：信令 / 会话生命周期端点；按仓库硬规矩要**同时改三处**（端侧实现 / `tools/mock-server.mjs` / `uni-app/api/README.md`） |
| `server/app/` | 无 GPU 依赖 | **新增**：会话编排、实例管理、成本与监控、鉴权与隔离 |
| `uni-app/common/face-gl/face-three.js` | 捏脸页在用 | 捏脸保端侧则**不动**；捏脸也上云则整体作废 |
| `uni-app/common/face/face-adapter.js` | 参数 → 四通道指令 | 若走"服务端把我们的参数换算成 MetaHuman 形态"，**新增**一层映射 |

**端侧改造量小（一个播放器 + 一个适配层）；工作量在云端那一半与资产重做。**

## 10. 建议的落地路径（分阶段，风险从低到高）

> 排序原则：**先解决"能不能做"（合规 + 技术可行性），再解决"值不值得做"（体验 + 成本）。**
> 因为本轮发现的两个最硬约束（§8.1 人脸上云、§3 Linux 断点）都会让后续投入归零。

**阶段 0（零风险，建议先做，与选型无关）——把"可切换"这件事做了**
- 把"数字人形象来源"抽象成一个 provider（`端侧 GLB` / `云端流`），通话页按 provider 播放；
- 好处：无论最终选 MetaHuman、别家云端、还是维持端侧，端侧改动都收敛在一个适配层里；
- 端侧落点很小（§9）：`pages/vision/vision.vue` 现在是 CSS 占位人形，
  换成"播放器 + 连接状态"即可，不需要动捏脸页。

**阶段 1（先问清，不写代码）——合规与技术可行性问询**
1. **合规问询（前置）**：带着 §8.1 的分析去找法务/合规顾问确认——
   "**表情驱动、非身份识别**"的人脸处理是否落入《人脸识别技术应用管理办法》第八条；
   若落入，需要哪些手续（单独同意、PIA、备案）与最坏情况下的成本；
2. **技术问询（前置）**：向 Epic 确认 **MetaHuman Animator 的 Linux 支持时间表**
   （官方当前明确"不支持 macOS 与 Linux"，Linux 支持仍是 "planned"）。
   若短期不会支持，则"云端实时面部驱动"这条路**现在就不具备可行性**，
   阶段 2/3 不必开始；可退而考虑"预渲染表情序列 + 云端播放"等折中形态（保真度换可行性）。

**阶段 2（可选，验证价值）——小规模灰度**
- 前提：阶段 1 两问都过关；
- 做法：捏脸仍走端侧 GLB（保住方案 §472 的判据）；仅通话页提供"高保真数字人"开关走云端；
- 规模：1~2 台 GPU 实例、限定少量用户，**先用按量或小时包，不要先买包月**；
- 测三件事：**端到端延迟是否可接受、老人是否买账、单路真实成本**（含 RTC 分钟费与带宽）。

**阶段 3（重投入）——全量云端**
- 只有阶段 2 的三项都被证明可接受才做；此时要重做资产管线、口型链路、降级策略与合规手续。

**不建议**：直接推翻端侧方案去上 MetaHuman——捏脸手感（产品硬判据）、
并发成本结构（§7.3）、人脸合规立场（§8.1）**三条会同时被破坏**，
而收益只是"更写实"，与原型图（`05_模型原型T-pose图/常服女/正面.png`，**风格化动漫脸**）也不一致。

## 11. 决策要点（请拍板）

1. **先决问题：目标是不是"更写实"？**
   若只是嫌当前资产不够写实，MetaHuman 的收益/代价比很低（且与原型图风格不符）。
2. **合规能否接受"面部数据/视频上云"？**（§8.1）
   若产品立场要求"真实面部不出手机"（与现有伦理红线同源），**云端方案就不必再评估**。
3. **能否接受"捏脸改异步"？**（方案 §472 判据的直接取舍）
4. **并发峰值预期？** 这一项直接决定成本量级：1,000 路 ≈ **376 万元/月**（§7.3）。
5. **谁来承担 UE/Linux 运维？** 云端方案需要长期运维能力（多实例、信令、监控、冷启动），
   而现团队的无头工具链是 Blender/Python，不是 UE/C++（§9）。

> 建议的默认答案：**维持端侧**；把阶段 0 的 provider 抽象做掉（低成本、不锁死未来），
> 并把阶段 1 的两个问询**在下一轮任何云端投入之前**问清。
