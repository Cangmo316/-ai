# 若改用 UE5 MetaHuman 做云端数字人 —— 改动面评估

> 用途：给"是否从端侧方案（uni-app + three.js + 自建 GLB）转向 UE5 MetaHuman 云端方案"提供可拍板的依据。
> 状态：**评估中**（调研员正在核实 MetaHuman 现行形态、授权、国内 GPU 与 RTC 价格，结果将补入 §2/§6/§7）
> 基线（当前方案的事实，均为实测）：端侧渲染；`uni-app/static/avatar/*.glb` 四件；
> 编辑期 60k 三角面 / 33 骨 / 113 `shape_*`；运行期 7 骨 / `vis_* 15 + expr_* 8`；
> 交付契约上限：**三角面 ≤60k、贴图 ≤2K、GLB ≤8MB、骨数 ≤70**（`比邻AI_数字人资产交付规范.md` §5）

---

## 0. 一句话结论（先给判断）

**技术上都做得到，但它不是"换个渲染器"，而是换一整套交付与运行体系。**
最贵的不是 UE，是三件当前方案"免费"、云端方案要花钱买回来的东西：

1. **捏脸的即时手感**（产品硬判据，方案 §472 已定"必须端侧"）——
   云渲染每拖一下要往返 200~500ms，手感必然崩坏。
2. **并发即成本**（端侧渲染的边际成本 ≈ 0；云端按"一路并发 = 一个 UE 实例"算，
   中等规格云渲染实例 **8.953 元/时 ≈ 单次 8 分钟通话 1.19 元算力**，
   且按峰值计费——康养场景"用户多、单次短、峰值集中"对云端最不友好）。
3. **面部数据不出端的合规立场**（现在老人的真实面部**从未离开手机**，
   上传的只是参数；改云端后要重新做单独同意 + 个人信息保护影响评估，
   且触碰《人脸识别技术应用安全管理办法》第八条"人脸信息不得通过互联网对外传输"的红线）。

**同时有一个降低评估风险的发现**：视觉模式（`pages/vision`）**目前是零实现**
（页面是 CSS 画的占位人形，端侧 API 与服务端都没有 vision 模块）。
所以现在做选择，**不是在改一套已有系统，而是在决定第一版怎么做**——
选择成本主要落在"要做的东西本身"，而不是沉没成本。

**建议**：不要推翻端侧。若要试，走 §10 的"阶段 0 + 阶段 1"（抽象 provider + 少量灰度），
用实测延迟与单路成本来决策，而不是先重投入。

## 1. 架构层面的改变（必然发生）

| 维度 | 现在 | 换 MetaHuman 云端后 |
|---|---|---|
| 渲染位置 | 手机本地 WebGL（three.js / renderjs） | 云端 UE5 实例（Linux + headless） |
| 资产格式 | `.glb`（Blender 导出，自建 33/7 骨） | UE 的 `.uasset` / MetaHuman 资产包（体积与结构完全不同） |
| 资产管线 | 我们自建的 Blender 无头管线（已有 20+ 工具、全套审计） | UnrealEditor-Cmd + MetaHuman 管线（**现有 Blender 管线对本方案无用**） |
| 端侧职责 | 渲染 + 应用 morph 权重 | **只做解码播放 + 收音频**（渲染权重全部移到云端） |
| 传输 | 逻辑层 → 端侧渲染器（同进程调用，0 延迟） | 端侧 ↔ 云端：WebRTC（信令 + 媒体）+ 控制通道 |
| 服务器 | 现在无 GPU 依赖（mock-server / agent 服务） | 新增 **GPU 渲染集群 + 信令服务 + RTC 转推** |
| 降级路径 | 三重降级（降帧 → 口型降级 → 静态形象） | 要多一条"云端不可用 → 回退端侧 GLB"或"纯语音" |

**关键结构性差异**：现在 `pages/face` 与通话页**共用同一份 `.glb` 与同一套参数**
（方案 §483），换成云端后这条"一份资产两处用"的链路会断——云端是 UE 资产，
端侧是 GLB，**要么维护两份形象、要么捏脸也上云**。

## 3. 口型/表情驱动链路的改变（**最容易被低估的一块**）

现在（已落地）：`TTS 音频 → 字级强制对齐 → viseme 曲线 → 端侧写 vis_* morph`，
方案 §340/§362 定义 15 个 viseme 组，`/v1/vision/session`（WS）把曲线下发端侧。

MetaHuman 云端方案下，这条链路要整体重做：
- MetaHuman **不吃我们的 `vis_*`**，它要 ARKit 风格 blendshape 或 UE 的音频驱动方案；
- 于是要么 **① 在服务端把 viseme 曲线重映射成 ARKit 52**，要么
  **② 改走"音频直驱"**（把 TTS 音频送进云端由 UE 侧做音频驱动口型）；
- ②更省事但把口型质量交给了 UE 侧的音频驱动方案，且**每个会话都要推音频上行**（带宽/合规）；
- 我们已建的 `morph-viseme-cosyvoice2.json`（jaw 角度标定）等标定**全部作废**，
  要在 MetaHuman 上重标一遍；
- 方案 §370 的"捏脸 morph 与口型 morph 分属两个命名空间"这条经验，
  在 MetaHuman 上由它自己的 Rig Logic 接管，**我们的两层分离设计不再适用**。

## 4. 产品体验上会破掉的两件事（与下一节同源）

1. **捏脸的即时手感**（方案 §472 的判据）：拖滑杆→云端往返 200~500ms/帧，手感必然崩。
   → 要么**捏脸仍走端侧 GLB**（那就得维护两份形象，且两边要长得像），
   要么**改成"选预设 + 异步生成"**（牺牲产品定义的核心体验）。
2. **低端机/弱网可用性**：现在有"首启能力探测 + 三重降级"；云端方案下，
   网络一抖就是画面卡顿/掉线，对**老人**是明显的体验与信任损伤，
   而且我们的"一键停止"红线要在流层面再实现一遍。

## 5. 延迟预算（**会直接撞上产品自己的指标**）

方案 §333 给视觉模式定的端到端预算是：**viseme 生成 + 渲染上屏 ≤ 100ms**。
云端方案要把这条链路拆成"上行/编码/网络/解码"四段额外开销：

| 环节 | 端侧（现在） | 云端（MetaHuman 方案） |
|---|---|---|
| 渲染 | 手机本地，同进程调用 | 云端 UE 渲染（+ 编码 H.264/AV1） |
| 画面传输 | **无** | 云端 → 端侧：网络 RTT + 编解码 + 抖动缓冲 |
| 口型驱动 | 服务端下发 viseme，端侧写 morph（同进程） | 需在云端生效（推音频或推 blendshape），**多一次上行** |
| 端到端典型量级 | 目标 ≤100ms（方案 §333） | **Pixel Streaming 的官方参考建议在局域网/专线做实测标定**（[Epic 官方 Pixel Streaming 参考](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-pixel-streaming-reference)），公网同城通常在**上百毫秒量级**，跨省更差 |

**这条对产品的实际含义**：
- "跟数字人对话"是**实时交互**场景，延迟每增加一档，老人感受到的是"她反应慢/卡住了"；
- 端侧方案的 100ms 预算在云端方案下**基本不可能保住**；
- 而这恰好是**康养场景最敏感的地方**（老人对"对面是不是活的"的判断更依赖即时反馈）。

> 诚实标注：我**没有**拿到"国内公网 Pixel Streaming 端到端延迟"的权威实测数字，
> 上面给的是量级判断。这个数字必须在阶段 1 用真实机型 + 真实网络**实测**，
> 而不是照抄任何厂商宣传值。

## 6. 需要新增的工程件（粗略清单）

- 云端：UE Linux 打包、headless 启动、MetaHuman 资产加载、多实例管理、健康检查、优雅回收
- 信令与媒体：Pixel Streaming 信令（或第三方 RTC）、TURN/STUN、码率自适应
- 端侧：`<video>` / RTC SDK 播放器、与现有 `pages/call` 的对接、延迟与断线处理

- 账号与安全：实例隔离（不同老人的会话不能串）、鉴权、录制与留存策略（如有）
- 回退：云端不可用时切回端侧 GLB 或纯语音 + 静态形象

### 7.2 并发模型（这决定成本能不能摊薄）

Epic 官方论坛对 Pixel Streaming 的定位说明（来源：
[Using Pixel Streaming 2 for Web Service](https://unreal2.epic-prod-us2.discourse.cloud/t/using-pixel-streaming-2-for-web-service-client-isolation-and-performance-questions/2496269/2)）：

> The PixelStreaming plugin (both 1 and 2) is **more designed for a 1 to 1 use case where
> there is one application per player connected**.

也就是说**行业默认是一路并发 = 一个 UE 应用实例**。多路共享同一实例虽然技术上可行
（音视频没问题，但输入设备无法区分 / 需要手柄），对"每个人是自己的数字人"这个场景
基本不可用（不同老人的形象不同、会话要隔离）。

### 7.3 量级估算（按"1 路 = 1 个 R 实例"算）

| 假设 | 数值 |
|---|---|
| 单路单价（取中等规格 gcs.r2c1m1.1xlarge） | 8.953 元/时 |
| 单次通话时长 | 8 分钟（≈0.133 小时） |
| **单次通话算力成本** | **≈1.19 元** |
| 单路全天常驻（24h） | 214.9 元/天 ≈ **6,447 元/月** |

按不同活跃度折算（**只算 GPU 算力，不含视频出云带宽 / RTC 分钟费 / 存储**）：

| 并发峰值 | 若按峰值常驻（元/月） | 若按"每天峰值时长 4h"（元/月） |
|---|---|---|
| 1 路 | ≈6,447 | ≈1,075 |
| 10 路 | ≈64,470 | ≈10,745 |
| 100 路 | ≈644,700 | ≈107,450 |

**结构性结论**：
- **端侧方案的边际成本 ≈ 0**（用老人自己的手机算力），成本与装机量无关；
- **云端方案成本随并发线性增长**，且康养场景"用户多、单次短、峰值集中（早晚问候）"
  对云端最不友好——**要为峰值付费，峰值之外实例闲置**；
- 另有未计入项：视频出云带宽或 RTC 分钟费（1080p30 通常需数 Mbps/路）、
  GPU 实例冷启动与排队、多地域部署（老人分布广，跨省延迟与就近接入）。

> ⚠️ 这些单价是**通用云渲染实例**的价格；UE+MetaHuman 的实际单实例密度（一路占多少 GPU 资源）
> 需实测才能给出准确单价。上面给的是**量级**，用于判断"这条路是否在预算内"。

## 8. 调研结论（授权 / 合规 / 价格）

### 8.1 合规（**这是本方案最硬的一道墙，且对养老产品尤其敏感**）

依据《人脸识别技术应用安全管理办法》（国家网信办、公安部令第 19 号，**2025-06-01 施行**）
——原文：[中国政府网](https://www.gov.cn/zhengce/zhengceku/202503/content_7016075.htm)：

| 条款 | 内容 | 对本方案的影响 |
|---|---|---|
| **第八条** | **除法律、行政法规另有规定或者取得个人单独同意外，人脸信息应当存储于人脸识别设备内，不得通过互联网对外传输** | ⚠️ **这是最关键的一条**：若我们采集/使用老人的面部信息并上传云端，原则上被禁止，除非取得**单独同意**或另有法定情形 |
| 第五条 | 事前以显著方式、清晰易懂的语言告知（目的/方式/保存期限/必要性/权利行使方式） | 设备端与 App 内要重新做告知页与流程 |
| 第五条末 | **处理残疾人、老年人人脸信息的，还应当符合国家有关无障碍环境建设的规定** | 老人场景**额外**要满足无障碍要求（适老设计不只是产品偏好，是合规项） |
| 第六条 | 须取得**单独同意**，且提供便捷的撤回方式 | 不能用"总隐私政策"打包同意 |
| 第九条 | 事前做**个人信息保护影响评估**并记录，报告**至少保存 3 年** | 要新增一项法务/合规工作量 |
| 第十五条 | 存储数量达 **10 万人**之日起 30 个工作日内向省级以上网信部门**备案** | 规模化后新增备案义务 |

**同时要指出一个对我们有利的边界**（第十二条定义的"人脸信息"与"人脸识别技术"）：
本办法规制的是**以人脸信息作为识别个体身份的个体生物特征识别技术**。
若我们只是"把用户做好的数字人形象拿去渲染"，而**不做身份识别/验证**，
仍须谨慎——**只要上传了面部图像/特征数据，就落进"敏感个人信息"的处理范围**，
仍受《个人信息保护法》约束（单独同意 + 影响评估 + 最小必要）。

**由此得出的产品级建议（与现有伦理红线同源）**：
- **尽量不上传真实面部**：捏脸走端侧（现在的做法）本身就规避了这条风险——
  老人的真实面部**从未离开手机**，上传的只是"参数"；
- 若要云端化，**优先只上传参数/预设，不上传照片或人脸网格**；
- 需要"像本人"时，考虑**端侧拟合、只传结果参数**，而不是把面部数据送云端。

## 9. 代码改动面（已对照仓库实际文件，**比想象中小很多**）

**先说一个决定性的事实：视觉模式目前是零实现。**

| 事实 | 证据 |
|---|---|
| 通话/视觉页的数字人是 **CSS 画的占位图形**（两个圆角块），没有 canvas、没有 3D 引擎 | `uni-app/pages/vision/vision.vue`（5KB，`.bl-vision__head` / `__torso`） |
| **没有 vision/viseme 会话的端侧 API** | `uni-app/api/config.js` 只登记了 chat / plan / elders / reminder / push / memory，**无 vision** |
| 服务端没有 vision 相关模块 | `server/app/**` 无 vision/avatar/stream 文件；`tools/mock-server.mjs` 也无 |
| 捏脸页是唯一真在跑 3D 的地方 | `uni-app/pages/face/face.vue`（23KB）+ `common/face-gl/face-three.js`（26KB） |

**含义（重要）**：P3「视觉模式」还没开始建。所以"换云端方案"**不是在改一套已有系统，
而是在决定第一版怎么做**——这比"推倒重来"便宜得多。选择成本主要落在**要做的东西本身**，
而不是沉没成本上。反过来说，已经建好的资产与工具链（Blender 管线、四件 GLB、
契约判据、H5 复验手段）若不走端侧路线，就成了纯沉没成本。

| 文件 | 现状 | 云端方案要做什么 |
|---|---|---|
| `uni-app/pages/vision/vision.vue` | CSS 占位人形 | **新增**：RTC/视频播放器 + 连接状态 + 降级（或保持占位人形作为降级档） |
| `uni-app/api/config.js` + 契约文档 | 无 vision 端点 | **新增**：信令 / 会话生命周期端点；按仓库硬规矩要**同时改三处**（端侧实现 / `tools/mock-server.mjs` / `uni-app/api/README.md`） |
| `server/app/` | 无 GPU 依赖 | **新增**：会话编排、实例管理、成本与监控、鉴权与隔离 |
| `uni-app/common/face-gl/face-three.js` | 捏脸页在用 | 捏脸保端侧则**不动**；捏脸也上云则整体作废 |
| `uni-app/common/face/face-adapter.js` | 参数 → 四通道指令 | 若走"服务端把我们的参数换算成 MetaHuman 形态"，**新增**一层映射 |

**端侧改造量小（一个播放器 + 一个适配层）；工作量在云端那一半与资产重做。**

## 10. 建议的落地路径（分阶段，风险从低到高）

**阶段 0（零风险，建议先做）——先不碰渲染，把"可切换"这件事做了**
- 把"数字人形象来源"抽象成一个 provider（`端侧 GLB` / `云端流`），通话页按 provider 播放；
- 这样后续无论选 MetaHuman 还是别家云端，端侧改动都能收敛在一个适配层里。

**阶段 1（可选，验证价值）——只给"视觉模式"做云端高保真档**
- 捏脸仍走端侧 GLB（保住 §472 的判据）；仅通话页提供"高保真数字人"开关走云端；
- 用 1~2 台 GPU 实例、限定少量用户灰度，测三件事：**延迟是否可接受、老人是否买账、单路成本**。

**阶段 2（重投入）——全量云端**
- 只有当阶段 1 的成本与体验都被证明可接受时才做；此时要重做资产管线、口型链路、
  降级策略与合规手续。

**不建议**：直接推翻端侧方案去上 MetaHuman——捏脸手感（产品硬判据）与并发成本结构
两件事会同时被破坏，而收益只是"更写实"，与原型图（风格化动漫脸）也不一致。

## 11. 决策要点（请拍板的三件事）

1. **目标是什么**：是嫌当前资产"不够写实"，还是想要"能拍视频级的高保真"？
   （若只是不够写实，MetaHuman 的收益/代价比很低）
2. **能否接受"捏脸改异步"**：这是 §472 判据的直接取舍。
3. **并发量级预期**：同时在线数字人通话的数峰值大概多少？这个数字直接决定成本量级是否可接受。
