# 音频与口型的两个真 bug：根因、修法、以及"我为什么没早发现"（2026-10-05）

> 用户实测反馈：**"并没有听到声音并且没有看到数字人唇形同步"**。
> 排查后确认这是我实现上的两个真 bug。本文记下根因与修法，
> 更重要的是记下**我的验证方法错在哪**——否则同类问题还会再犯。

---

## Bug 1：mock 的音频实际只有 **0.052 秒**

### 现象与根因

我用"两帧静音 MP3"（417 字节 × 2）想造约 1 秒的音频。
实测浏览器 `loadedmetadata` 给出 **`duration = 0.052125`** —— 只有 52 毫秒。
**所以就算整条链路全通，用户也听不到任何东西**，口型也是一闪而过。

### 我的验证错在哪（这条比 bug 本身更值得记）

当时的断言是：

```js
check('字节像 MP3（帧同步字 0xFF 0xF?）',
  bytes[0] === 0xFF && (bytes[1] & 0xE0) === 0xE0)
```

**这是形状断言**：只确认了"头几个字节长得像 MP3"，完全没管**时长**。
形状对、时长错 —— 断言通过、功能是坏的。

### 修法

mock 改用**运行时生成 3 秒静音 WAV**（`buildSilentWav`）：静音时长可精确控制、
任何浏览器都能解码、不需要编码器。`durationMs` 与字节数严格对应，
`Content-Type` 如实改为 `audio/wav`。

断言也同步换成**行为断言**（`tools/test-audio-channel.mjs`）：

```
✓ 字节与声明的格式一致（wav）        ← 不再是"像 MP3"
✓ 音频实际时长 ≥ 2 秒                ← 直接防住"52ms"这类问题
✓ durationMs 与字节算出的时长一致（±0.2s）
```

## Bug 2：口型的时钟在音频就绪**之前**就起跑了

### 现象与根因

原来的实现是：播放器从 `lipsync.start()` 那刻起跑一个**自有时钟**，
音频另外异步加载（要**下载 + 解码**，实测几百毫秒到几秒）。

结果：**嘴在这段等待时间里已经把整句演完了**；等声音出来时嘴已经停了。
用户看到的正是"没有唇形同步"。

根因是设计错误：**两个时钟各自跑，再想办法对齐**。
而且我当时的"对齐"手段是 `resync()` + 100ms 轮询 `onTimeUpdate`——
粒度粗、且**根本无法弥补"起跑太早"**（嘴已经空转完了）。

### 修法：单一时间源

把时间源做成**可注入**，有真音频时**只用一个时钟**：

```js
const lipsync = createLipsyncPlayer({
  clock: () => {
    if (!audioContext) return null          // 音频还没挂上 → 返回 null
    return Number(audioContext.currentTime) * 1000
  },
  onFrame: (frame) => stageRef.setVisemes(frame),
})
```

**音频播到第几毫秒，嘴就摆到第几毫秒**——不存在漂移，也就不需要"校准"。

配套细节（都是踩坑得来的）：
- `clock()` 返回 `null`/非数字时**退回自有时钟**，而不是当作 0：
  当作 0 会让嘴卡在句首；而没有音频时（后端未配 TTS）更需要自有时钟把整句演完。
- 口型**立刻挂上**、不等 `onPlay`：音频没就绪时 `currentTime` 为 0（嘴停在句首），
  开播后自然跟着走——**不会漏掉开头**。
- 删掉了 `resync()` 轮询：单一时间源下它是多余的。
- `stats().clockSource` 如实报告 `'audio' | 'self'`——"嘴跟的是不是声音"必须可观测。

## 行为验证（这次是真的）

**先说清上一版的问题**：我的验证页自己 `send()`，却去读 `window.__blVisionAskStats()`
——而**渲染舞台在通话页里**，所以读到的是空值。这又是一次"看起来在验证"。

**改成在通话页内做行为探针**（`__blVisionProbeStart()` → `ask()` → `__blVisionProbeResult()`），
每 200ms 同时采「音频位置 + 当前形态键权重 + 时钟来源」：

| 判据（都是**行为**，不是形状） | 实测 |
|---|---|
| 音频时长 | **3.0 秒** ✓ |
| **嘴真的动了** | `mouthMoved: true`，**167 / 326 个采样点**有非零 viseme 权重 ✓ |
| **时钟来自音频** | `clockFromAudio: true` ✓ |
| 音频真的起播 | `played: true`、`error: ""` ✓ |

开头几个采样是 `t: -1 / clock: "self"`（音频还没挂上），之后立刻切到 `audio`
—— 正是设计中的降级路径在起作用。

## 三条教训（写给以后的自己）

1. **形状断言 ≠ 行为断言**。"字节像 MP3" 通过了，但音频只有 52ms。
   对音频要断言 **duration**；对 3D 要断言**形态键权重**；对接口要断言**业务结果**。
2. **数据到达 ≠ 功能生效**。"音频 URL 到了端侧" 不代表"响了"；
   "cues 收到了" 不代表"嘴动了"。
3. **两个时钟各自跑必然漂移**。音画同步只有一个正确做法：**单一时间源**。
