# 通话页接对话流：数字人真的开口说话（2026-10-05）

> 闭环的最后一环：**老人问一句 → SSE 流式回答 → 数字人边说边动嘴**。
> 承接：`唇形同步接线_方案A.md`（口型）、`音频下发通道.md`（音频下发）。

---

## 1. 为什么不另写一条 SSE

仓库约定：**家人端与老人端共用 `uni-app/api/` 那一层客户端**。
而 `stores/chat.js` 已经把 SSE 解析、幂等（`clientMsgId`）、一键停止、重试、
断流兜底全都处理好了。在通话页再写一套 = 两份实现，日后必然走偏。

所以只给 store 加了一个**实时事件订阅**，通话页按需接：

```js
// stores/chat.js（新增）
export function onLiveTurn(listener)   // 订阅"这一轮数字人说完"的完整数据
```

### 为什么"订阅"而不是把音频塞进聊天历史

`audio`（签名 URL）与 `lipsync`（口型关键帧）都是"说完才发"的**瞬时数据**：
- 签名 URL **几分钟后就过期**，存进历史毫无意义；
- 聊天历史里存的是文字/表情/卡片——**音频与口型不该污染它**。

所以走订阅：历史保持干净，通话页实时拿。

## 2. 一轮说完整的数据流

```
老人：ask("今天天气怎么样")
  → stores/chat.js  send()  → chatStream(SSE)
      ├─ token  ..n        → 聊天消息（历史）+ 通话页字幕实时上屏
      ├─ audio             → turn.audioUrl（签名 URL）
      ├─ lipsync           → turn.cues（viseme 关键帧，≤2 个/帧）
      └─ done              → emitLiveTurn({ text, audioUrl, cues, lipsyncSource })
  → 通话页 onLiveTurn 回调
      ├─ 有 audioUrl → playTurn(url, cues)：音频 + 口型**一起起播**
      └─ 无 audioUrl → playLipsync(cues)：只动嘴（后端没配 TTS 时）
```

**顺序的意义**：`audio` 必须在 `lipsync` 之前（服务端保证），
端侧攒齐两者再一起起播——这样口型与音频**从一开始就对齐**，
并在音频真正开始时 `resync()` 把驱动层基准切到音频时钟。

## 3. 交互（适老）

| 控件 | 行为 |
|---|---|
| **问一句**（输入框 + 按钮） | 走**真对话流**，数字人边说边动嘴。暂时用"打字"代替说话，等 ASR 接上后换成按住说话 |
| **停一下** | 产品红线：老人随时可停。停音频 + 停口型 + `chat.stop()` 停流式 |
| **让 TA 招手** | 播交付件里的 `wave` 动画（与对话流独立） |
| 字幕 | 就是数字人说出来的话（流式上屏，与服务端 `token` 同步） |

> "停一下"做成**一等公民**（与招手并排、够大）不是随手加的：
> 产品红线要求"老人可一键停止"，而这个页面是唯一会出声的地方。

```

lastTurn.cueCount: 12                            ← 口型关键帧条数
```

**证据链完整**：从"打字提问"到"字幕上屏 + 音频签名 URL 到达端侧 + 口型关键帧"。

## 6. 还没做

1. **没有语音识别（ASR）**：现在用输入框"打字"代替说话。老人的真实入口应是"按住说话"，
   这需要 ASR（选型文档里列的是云 API，与"语音不出网"的取向需另行决策）。
2. **没有"打断"（barge-in）**：老人一开口就应停掉数字人。`stopAudio()` 已有，
   缺的是**语音活动检测（VAD）**去触发它。
3. **每轮都重新合成**：百炼按字计费；固定话术（如"该吃药了"）值得做音频缓存。
4. **通话页与聊天页是两个入口**：目前各自独立。要不要把通话页做成"聊天页的语音模式"
   （共享同一会话与历史）是个产品决策——技术上已经共用同一个 store，改起来不难。
5. **端侧音频时钟的真机验证**：`currentTime` 的 `onTimeUpdate` 粒度只在无头浏览器里间接验证过，
   真机上是否够稳**未实测**（驱动层已支持 `resync()` 任意时钟，太粗可改用起播时间自算）。
