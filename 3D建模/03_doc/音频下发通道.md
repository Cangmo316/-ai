# 音频下发通道：让数字人真的开口说话（2026-10-05）

> 承接：`唇形同步接线_方案A.md`（口型）与 `CosyVoice2与字级对齐_部署指南.md` §6（百炼 Qwen-Audio-TTS）。
> 那份文档的"仍然没做"第 1 条就是本文件解决的事：**合成音频怎么送到端侧播放**。

---

## 1. 核心约束：播放器带不了 `Authorization` 头

端侧播音频只有两条路，**都没有办法加请求头**：
- App：`uni.createInnerAudioContext().src = url`
- H5：`<audio src=url>`

而本项目的鉴权（`server/app/auth.py` 的 `extract_token()`）**只从请求头取 token**。
所以音频不能走"普通鉴权端点 + 带 token 请求"。

**解法：短期签名 URL**（行业常规做法，S3 预签名 URL 同理）——
把"这份音频、到这个时刻为止、可以取"编进 URL 查询参数，端点自己校验签名与有效期。

```
GET /v1/audio/<audio_id>?expires=1699999999&sig=<hmac32>
```

签名：`HMAC-SHA256(key, "<audio_id>.<expires>")` 取前 32 位 hex，校验用 `hmac.compare_digest`（常量时间）。
密钥优先 `BILIN_AUDIO_SECRET` → 否则从 `API_TOKENS` **派生**（`sha256("bilin-audio:" + tokens)`）→
都没有则进程级随机（重启后旧 URL 失效，可接受：音频本来就只活几分钟）。
**刻意不让签名密钥等于 API token** —— 泄露签名的危害面要更小。

## 2. 暂存策略（刻意从简，理由都写下来了）

| 决定 | 理由 |
|---|---|
| **只在内存**存音频，TTL 10 分钟 | 老人语音是敏感信息（PIPL）：不落磁盘 = 进程退出即消失，不必做清理与磁盘加密 |
| 总量上限 64MB，超了丢**最旧的** | 音频是一次性的，丢旧的比丢新的合理 |
| `audio_id` 是随机 32 位 hex，**不含任何业务标识** | 日志与 URL 里都不出现老人/会话 id |
| 未做多进程共享 | 单进程原型够用；要横向扩展就把 `_STORE` 换成 Redis/S3，**签名与接口形状不用改** |

## 3. 事件顺序（**这是端侧能对齐音画的前提**）

```
… token…  →  audio  →  lipsync  →  done
```

**为什么 `audio` 必须在 `lipsync` 前面**：端侧要先拿到音频、起播，
才能用"音频当前播放到第几毫秒"驱动口型。顺序反了端侧只能凭猜，
音画必然漂移（而且误差会累积）。

端侧拿到后一起起播（`player.start(cues)` + `audio.play()`），并在音频真正开始播时
`resync()` 把驱动层基准对齐到音频时钟；之后每 100ms 用 `currentTime` 持续校准。
**帧间仍由 30fps 的自有时钟平滑推进** —— `onTimeUpdate` 回调粒度粗，不能直接驱动 30fps。

## 5. 为什么 mock 要真发一段能解码的 MP3

给一段假字节的话，播放器会报错、端侧走降级分支，**表面上看不出问题**。
所以 mock 运行时生成一个合法的 MPEG1 Layer3 帧（帧头 `FF FB 90 64` + 静音负载，两帧约 830 字节），
这样"端侧真的能播"才算被验证过。

## 6. 实测

**端到端（对着 mock 服务跑 `npm run test:audio`）**：**13/13**

```
✓ 流里出现 audio 事件
✓ audio 在 lipsync 之前（否则端侧无法用音频时钟驱动口型）
✓ url 带签名与有效期（expires + sig）
✓ 签名 URL 能取到音频（HTTP 200）
✓ Content-Type 是音频
✓ 字节像 MP3（帧同步字 0xFF 0xF?）
✓ 签名错误取不到（403）   ✓ 篡改 id 取不到（403）
✓ 不带签名取不到（403）   ✓ 过期签名取不到（403）
```

**三套测试**：`npm test` 全绿；`npm run test:face` 20 + 9；后端 `unittest` **355 项**（原 336 + 新增 19）。

> `npm run test:audio` 需要先起 mock（`node tools/mock-server.mjs --port 8787`），
> 所以**没有**并进 `npm test` —— 那条命令必须保持零外部依赖。

## 7. 还没做 / 已知限制

1. **通话页仍没有对话流入口**：`playTurn()` / `playSpeech()` 已就绪，但页面还没接 SSE 流，
   目前靠 `window.__blVisionPlayTurn(url, cues)` 手工触发。接线要做的是把聊天流的事件转给通话页。
2. **没有音频缓存**：每轮都重新合成（百炼按字计费），重复话术可考虑缓存。
3. **没有"打断"**：老人说话时数字人应停止播放（`stopAudio()` 已有，但没有语音活动检测去触发它）。
4. **端侧时钟校准只用了 `currentTime`**：真机上 `onTimeUpdate` 粒度未实测，
   若粒度过粗可改用 `getDuration()` + 起播时间自算（驱动层已支持 `resync()` 任意时钟）。
5. **音频格式固定按 mp3 处理**：百炼默认输出 MP3；若改 WAV，服务端 `media_type` 与端侧扩展名都要跟着改。
