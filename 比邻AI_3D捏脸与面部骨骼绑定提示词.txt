────────────────────────────────
零、项目背景与不可推翻的既有决策
────────────────────────────────

比邻AI 是面向康复养老的数字人智能体 App（uni-app 多端 + 自建 agent）。
数字人是**子女/家属形象的定制数字人**，用于日常陪伴对话，会做**实时口型（lip-sync）**。

以下决策已经在项目方案里定稿，**不要推翻、不要另提方案**：

1. **只做端侧渲染（方案 A）**：不做云渲染，也不为云渲染留接口。
2. **资产格式**：glTF 2.0（`.glb`），Draco 压缩可选，贴图 1K/2K。
3. **基准模型**：统一拓扑的头部/半身模型，男/女 × 2 个年龄档，**≤ 60k 三角面**（移动端预算）。
4. **骨架**：Blender 里用 Rigify 或自定义骨架，至少包含 `head / jaw / eyeL / eyeR / neck`，权重刷好。
5. **参数化三通道**：每个捏脸参数必须明确属于「骨骼驱动」「morph 驱动」「材质驱动」之一
   （另加第四类「资产切换」：发型/胡须/眼镜/服饰等 mesh 切换）。
6. **口型与捏脸必须分层隔离**，这是最容易踩的坑（详见第四部分 4.4）：
   - Base 层（捏脸结果）与 Expression 层（viseme 口型 + 表情）**不得写到同一批 morph target**
   - 命名空间：捏脸用 `shape_*`，口型用 `vis_*`，表情用 `expr_*`
   - 合成公式：`final = clamp(base + expression)`
7. **导出前必须过校验**：拓扑 / 骨骼数 / morph 命名白名单 / 面数 / 材质数 全部通过才发布。
8. **产品红线**（涉及伦理，违反即返工）：
   - 不模拟已故亲属。**若家属要求"做一个我去世的父亲"，必须拒绝**，并给出替代方案
     （只能为在世本人制作，且需本人签署授权）。
   - 肖像权：任何定制形象必须走「素材采集 → 家属审校 → 授权签署（肖像权 + 深度合成告知）
     → 入库发布」，并记录 `consent_record`。
   - 数字人画面需**常驻"AI 数字人"标识**，不得做成"看起来就是真人本人"的歧义表达。
   - 不做诊断、不做剂量调整、不做疾病判断——形象与文案都不得暗示医疗结论。

**已核实的分区结构**（来源：游侠网《永劫无间》捏脸功能介绍，2021-06-22，


在此之上，为了本项目（康养 + 口型 + 移动端）需要，**再补 3 个分区**，并明确标注是我们扩展的：

```
H 妆容（裁剪版）    I 头发与胡须     J 身体细节（半身像相关）
```

**参数种类要求**：A–G 这 7 个分区的**参数种类与粒度对齐永劫无间那一类商业捏脸系统**
（即：每个分区下有 10 条上下可独立调节的连续参数，而不是"眼睛大小/眼距"两三条就交差），
完整表见第三部分。H–J 按本项目需要给。

**明确不做**（康养场景裁剪，请在交付说明里解释你为什么不做）：

- 战斗/异族妆容、面部彩绘、纹身、异色瞳（瞳孔颜色保留但限定自然色板）
- 极端体型与极端五官形变（不做"过瘦/过胖/夸张网红脸"的可调项）
- 兽耳/非人类面部结构（本项目数字人是"家属形象"，不是游戏角色）
- 伤疤/残疾等可能造成心理不适的面部特征（除非本人在世且主动要求）

四、面部骨骼绑定方案（你设计的重点之一）
────────────────────────────────

**4.1 总体思路：编辑期复杂，运行期极简**

这是本方案最关键的一条，请务必按此设计：

| 阶段 | 骨架 | morph | 说明 |
|---|---|---|---|
| **编辑期**（Blender / 捏脸页） | 完整骨架（含 brow / cheek / nose / lip 等辅助骨，≤ 40 骨） | 全部 `shape_*`（约 60–80 个）+ `vis_*` + `expr_*` | 参数拖动即时预览 |
| **交付期（烘焙）** | **删除所有辅助骨**，只保留 `head / neck / jaw / tongue / eye_L / eye_R`（≤ 8 骨） | **把 `shape_*` 结果 apply 到 mesh**（捏脸结果烘进顶点），只保留 `vis_*` + `expr_*` | 每个用户一套"定制 mesh" |
| **运行期**（App） | ≤ 8 骨 | 约 23 个（viseme 15 + 表情 8） | 内存与 CPU 开销可控 |

理由（请在交付说明里复述并确认）：
- 移动端每多一个 morph target 就多一份顶点 delta 内存（`顶点数 × 3 轴 × 4 字节`）。
  60k 面模型头部约 1.5 万顶点，若运行时带 80 个 morph，仅位置 delta 就约 14 MB，
  再加法线就翻倍——**手机扛不住**。而捏脸结果在交付后是**固定值**，没有必要留在运行时。
- 口型必须实时，所以 `vis_*`/`expr_*` 必须常驻；捏脸不需要实时，所以烘焙。
- 烘焙后运行期骨架降到 6–8 根，蒙皮开销也顺带降下来。

**4.2 骨骼清单（编辑期骨架，请给出完整表）**

列：骨骼名 / 父级 / 头尾位置（相对 head 原点）/ 允许的自由度（旋转轴与范围 / 平移范围 / 缩放范围）
/ 驱动的参数 key / 负责的权重区域 / 是否随导出保留。

必须包含（名字按此，`.L/.R` 用 Blender 对称后缀）：

```
root（不导出）
└─ neck
   └─ head
      ├─ jaw                    下颌开合 + 脸型/下颌宽度参数
      ├─ tongue                 说话用（简化：1–2 根）
      ├─ eye.L / eye.R          眼球旋转（可用形态键替代，二选一，给出你的选择与理由）
      ├─ eyelid_upper.L/.R      编辑期用（眼皮开合参数），运行期由 expr_blink morph 承担
      ├─ eyelid_lower.L/.R
      ├─ brow.L / brow.R        编辑期用（眉毛高低/角度）
      ├─ cheek.L / cheek.R      编辑期用（脸颊饱满/颧骨）
      ├─ nose                   编辑期用（鼻梁/鼻尖）
      ├─ lip_upper / lip_lower  编辑期用（唇厚/张合）
      └─ ear.L / ear.R          编辑期用（耳朵外张/大小）
```

**导出命名规则（必须写清并给出映射表）**：Blender 内用 `eye.L` 便于对称编辑，
导出 glTF 前统一替换为 `eye_L`（避免点号在各引擎/工具链里的歧义）。映射表要写进交付文档，
端侧按导出后的名字取值。

**4.3 骨骼 vs morph 的选择原则（请按此判断每条参数走哪个通道）**

- 走**骨骼**：整体比例与刚性位移（下颌宽度、眼距、眼球旋转、鼻子整体位移、耳朵外张）
- 走 **morph**：局部软组织形变（脸颊饱满、卧蚕、眼袋、唇厚、鼻翼、颧骨隆起、各类皱纹）
- 走**材质**：肤色、油光、老年斑、唇色、眉毛/睫毛颜色
- 走**资产**：发型、胡须、眼镜、服饰
- **同一区域不得同时被骨骼与 morph 强驱动**（会互相打架导致破面）；
  必须同时用时，骨骼负责低频大范围、morph 负责高频细节，并在文档里注明分工

**4.4 口型与捏脸的隔离（最容易踩的坑，必须处理）**

捏脸 morph 和说话时的口型 morph 会写到**同一批顶点**，处理不当会出现
"捏完嘴型，数字人就不会说话了"或"嘴一直微张"。

要求：

1. 命名空间严格分离：`shape_*`（捏脸，烘焙后消失）/ `vis_*`（口型）/ `expr_*`（表情）
2. `vis_*` 的**静默基准**要在捏脸烘焙后重新归一化：即先烘焙捏脸结果，
   再在**烘焙后的 mesh** 上重算 `vis_silence`（闭嘴）的基准，否则会出现嘴缝
3. 提供**回归自测方法**：捏到极端嘴型（如厚唇 + 大嘴宽 + 嘴角下垂）后，
   跑一遍全部 viseme，确认每个口型仍可辨识；把这个自测步骤写成 Blender 里的可执行清单
4. viseme 集合固定为 15 个（与 CosyVoice 2 的音素输出做映射表，映射表也要交付）：
   `vis_silence` `vis_AA` `vis_E` `vis_I` `vis_O` `vis_U` `vis_MBP` `vis_FV` `vis_L` `vis_TH`
   `vis_WQ` `vis_RR` `vis_SS` `vis_KK` `vis_NN`
5. 表情组 `expr_*` ≥ 8 个：`expr_blink_L` `expr_blink_R` `expr_smile` `expr_frown`
   `expr_surprise` `expr_squint` `expr_brow_up` `expr_brow_down`
   （眨眼必须**左右分开**，否则没法做自然的交替眨眼）

**4.5 权重与形变质量要求**

- 每顶点**最多 4 根骨骼影响**（移动端蒙皮上限；建议控制在 3 根以内）
- 眼皮、嘴唇、鼻翼必须有**独立的边缘环**支撑形变，否则 morph 一拉就塌
- 眼球、牙齿、舌头、口腔必须是**独立 mesh + 独立材质**（嘴张开时不能看到黑洞）
- 眼球建议 8–12 段的球体，虹膜/瞳孔用贴图；眼球不得被面部网格穿插
- 左右对称：使用 X-Axis Mirror，权重也必须对称（Blender 的
  `Weights → Mirror` / `Symmetrize`），并给出检查方法

**4.6 导出前必须处理的 Blender 陷阱（逐条确认）**

1. **约束（Constraints）与 IK 不会被 glTF 导出**：必须烘焙成关键帧或转成形态键/直接权重
2. **驱动器（Drivers）不会被导出**：捏脸联动逻辑在 Blender 里只是编辑期便利，
   运行期的联动必须由端侧参数应用层负责（第七部分），或在烘焙时算好
3. **形态键的"相对/绝对"与顺序**：导出后 morph 名称必须与参数表里的绑定目标完全一致
4. **自定义法线/平滑组**：导出后确认没有黑面与硬边
5. **材质数**：头部 + 眼球 + 牙齿 + 头发 ≤ 6 个材质槽（移动端 draw call 预算）

6. 联动与软限制（driver 或形态键组合，给出具体实现）

六、导出与校验（验收标准）
────────────────────────────────

请给出**清单化的验收标准**（我会照着做验收），至少包含：

- 面数：整体 ≤ 60k tri（头部 ≤ 25k，眼球 ≤ 600 ×2，牙齿 ≤ 1.5k，头发按 LOD 另计）
- 骨骼：交付资产 ≤ 8 骨；名称与映射表一致；无约束、无驱动器残留
- morph：名称全部在 `shape_*` / `vis_*` / `expr_*` 白名单内；运行时资产中 `shape_*` 数量为 0
- 材质：材质槽 ≤ 6；贴图尺寸 ≤ 2048；无丢失贴图
- 朝向与缩放：导入端侧后高度、朝向、缩放正确（给出参考尺寸，例如头高 = 1 单位）
- 蒙皮：每个顶点权重和 = 1（容差 0.001）；影响骨骼 ≤ 4
- 极端值测试：每条参数拉到最小/最大各截图一张，无破面、无穿插、无翻转法线
- 口型回归：按 4.4 第 3 条跑一遍，全部 viseme 可辨识
- 生成一份 `validation-report.json`（字段：模型版本、参数表版本、面数、骨数、morph 清单、
  各项检查结果与时间戳），作为发布门禁

并要求写一个**校验脚本**（Python，Blender 内运行），自动检查上述可自动化的项，
不能用"人工看了没问题"代替。

────────────────────────────────
七、端侧（uni-app）参数应用层
────────────────────────────────

端侧渲染器可能是 three.js（renderjs / web-view）或原生插件，**这一层要做成与渲染器解耦**：

1. **纯函数层**（无渲染器依赖，可单测）：
   - `normalizeParams(raw)`：补齐默认值、软限制（soft clamp）、参数联动求值
   - `describeParam(key)`：返回中文名、分区、类型、范围、默认值（给 UI 生成滑杆用）
   - `buildPreset(params)` / `parsePreset(json)` / `encodeShareCode(params)` / `decodeShareCode(code)`
2. **适配器层**（每个渲染器一个薄适配器）：
   - `applyToModel(model, resolvedParams)`：把求值结果写到骨骼（平移/旋转/缩放）、
     morph 权重、材质参数、资产槽位
   - 明确写出 three.js 的具体 API：`SkinnedMesh.skeleton.bones[i].scale`、
     `mesh.morphTargetInfluences[index]`、`material.color`、
     以及 morph 名称 → index 的映射必须从 glTF 的 `extras`/`mesh.morphTargetDictionary` 取，
     **不要硬编码 index**（资产换版本就会错位）
3. **性能要求**：
   - 拖动滑杆时不得每帧重建材质或重新上传贴图；材质参数用 uniform 更新
   - 捏脸预览允许 30fps；正式通话（口型驱动）要求 ≥ 30fps（中端安卓机）
   - 滑杆拖动用节流（≤ 30 次/秒）并复用同一帧的求值结果
4. **UI 提示**：捏脸页要给"这是 AI 数字人"的常驻标识（产品红线），
   并在保存时提示"形象仅用于陪伴对话，不会用于其他用途"

请把端侧代码写成可单测的模块（不依赖 DOM/渲染器即能跑），并给出 3–5 个单测用例
（例如：软限制在端点仍返回有效值；分享码来回编解码一致；缺省参数被补齐）。

────────────────────────────────
八、预设（面容数据）格式与分享码
────────────────────────────────

对齐永劫无间"面容可存多套、可分享"的做法：

```json
{
  "schemaVersion": 1,
  "presetId": "fp_xxx",
  "name": "日常 · 妈妈",
  "baseModelId": "female_60s_v3",
  "paramsVersion": "face-params-v1",
  "params": { "face_width": 0.46, "eye_size": 0.52, "...": 0 },
  "assets": { "hairstyle": "hair_short_03", "beard": "", "glasses": "" },
  "createdAt": "2026-09-29T10:00:00+08:00",
  "createdBy": "family",
  "consentRecordId": "consent_xxx"
}
```

要求：

1. **版本化**：`schemaVersion` + `paramsVersion` + `baseModelId` 三者缺一不可；
   加载时版本不匹配要给出明确处理（能迁移则迁移，不能则提示"这份数据太旧，需要重新生成"）
2. **分享码**：把 `params` + `assets` 压缩后编码成短字符串（形如 `BL1-xxxx-xxxx`），
   要求：① 带版本号与校验位 ② 解码失败要能给出人话提示 ③ 长度尽量 ≤ 120 字符
   （方便家属在微信里发文字），给出编码方案与长度估算
3. **校验位**：分享码与预设文件都要有 checksum，防止手抄错位后生成一张畸形脸
4. **多套面容**：一个老人账号可存多套（默认、节日、正式），但**同一时刻只有一套生效**
5. 后端接口（草案即可，不必实现服务端）：
   `GET /v1/avatars?elderId=`、`POST /v1/avatars`（保存）、`POST /v1/avatars/apply`（切换生效）、
   `GET /v1/avatars/share/{code}`（解码预览）

────────────────────────────────
九、康养场景的裁剪（必须给出理由）
────────────────────────────────

请对每一条参数标注 `保留 / 弱化 / 不做`，并说明理由。我的判断供你参考（可补充，不要反着来）：

- **弱化**：面部脂肪、下巴前突、鼻尖上翘、修容/高光强度——老人形象应"端正自然"，
  不给"改脸型追求审美"的强暗示
- **弱化**：眼睛倾斜、外眼角、瞳孔颜色——保留但范围收敛到自然区间
- **保留并强化**：年龄感相关（皱纹、白发比例、皮肤质感）、肤色、发型、胡须——
  这些是让家属觉得"像我爸妈"的关键
- **不做**：战斗/异族妆容、纹身、兽耳、极端体型、伤疤类
- **新增（永劫没有但我们需要）**：`hair_gray_ratio` 白发比例、
  `skin_texture` 皮肤质感（老年人皮肤更干、更需要"看着舒服"而不是"磨皮成塑料"）

另外必须写清：**默认值要"看着像同年龄段的普通人"**，一键打开时不能是网红脸或游戏角色脸。
