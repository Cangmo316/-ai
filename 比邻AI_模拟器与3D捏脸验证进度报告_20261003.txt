2.4 关键诊断结论 —— App 端跑不起来的两层根因（本轮最有价值的产出）
    【第一层】基座 APK 的 ABI 与 x86_64 模拟器不匹配
      - HBuilderX 标准基座 android_base.apk 只带 arm64-v8a / armeabi-v7a / x86，
        没有 x86_64（已用 zip 条目核对：arm64-v8a 51 个、armeabi-v7a 51 个、x86 48 个）。
      - API 34 x86_64 镜像的 abilist = x86_64,arm64-v8a，且 abilist32 为空，
        原生桥为 libndk_translation.so；于是安装器只能挑 arm64-v8a，走 ARM 翻译层。
      - 后果：weex（uni-app 逻辑层 JS 引擎）的多进程 IPC 在翻译层下起不来：
          E/WeexCore: WeexJSConnection catch: spinWaitPeer timeout
          E/WeexCore: IPCException server spinWaitPeer timeout
          E/WeexCore: script_side_in_multi_process.cpp:43,InitFramework sender is null
          E/weex: [WXBridgeManager] invokeInitFramework ExecuteJavaScript fail
          E/weex: framework.js uninitialized
        → 应用永远停在 HBuilder splash（PullDebugActivity），60fps 只是 splash 转圈动画。
      - 排除项（都已验证过，不是原因）：
          资源同步成功（apps/HBuilder = 35 MB，说明 wgt 与 32 MB GLB 都进了设备）
          无 UnsatisfiedLinkError
          manifest.json 的 appid 为空**不是**阻塞（基座用 appID:"HBuilder" 兜底）
          网络正常、磁盘充足

四、下一步选项（含代价，供你选）

A. 用真机（arm64）—— 最可靠，**我推荐这条**
   一台 Android 手机开 USB 调试即可。基座 arm64 原生运行，无翻译层、无解压崩溃，
   也顺带覆盖 renderjs 宿主黏合。
   命令：
     E:\download\HBuilderX.5.26.2026091802\HBuilderX\cli.exe launch app-android ^
       --project "E:\比邻AI\uni-app" --deviceId <手机序列号> --pagePath pages/face/face
   成本：0 下载；需要你有一台手机。

B. 换更低版本 x86 镜像（android-28 或 android-29 的 x86）—— 中等成本
   赌不同 ART 版本不复现该解压崩溃。成本：每次约 1 GB 下载 + 建 AVD + 1 次冷启动。

C. 继续在现有 x86 镜像上试规避 —— 低成本，成功率不确定
   即被中断的那一步：关 JIT（已关）/ 重启框架 / 或试 -accel off（纯软件，很慢）/
   或换 -gpu swiftshader_indirect。

D. 第三方模拟器（MuMu 12 / 雷电）—— 约 1 GB 安装
   x86 内核，社群反馈用它跑 uni-app 标准基座较常见。本机还有 MuMu 的虚拟化残留
   （C:\Program Files\MuMuVMMVbox），但主程序已不在。

E. 只停在 H5 验证 —— 成本 0，但**覆盖不到 renderjs 宿主黏合**，
   而这正是你最想确认的那件事（原生 switch/slider 渲染 + renderjs 是否真能挂上 WebGL）。

建议顺序：A > B > D > C。若你没有安卓真机，我建议先 B 再 D。

--------------------------------------------------------------------------------
最终结论
--------------------------------------------------------------------------------
HBuilderX 标准基座 android_base.apk 带三套原生库（arm64-v8a / armeabi-v7a / x86），
在本机 "Windows + WHPX + 官方 Android 模拟器" 上，三条 ABI 路径全部不可用：
    arm64 路径 -> 只能靠 libndk_translation 翻译，weex 多进程 IPC 挂掉
    x86   路径 -> 32 位客体不稳定；且基座在解压同步包 / 初始化 WebView 时段错误
这不是比邻AI 项目代码的问题：改动前后现象一致，所有崩溃都落在 io.dcloud.* 的代码里。
继续在官方模拟器上"规避"的收益已经很低，建议改走真机。

推荐（依据比 §4 更充分）
  A. 真机（arm64）—— 首选。基座走 arm64 原生路径，是该基座最主流、测试最充分的路径，
     同时正好覆盖你最想确认的 renderjs 宿主黏合。成本：一台安卓手机，0 下载。
  B. 第三方模拟器（MuMu 12 / 雷电）—— 约 1 GB 安装，自带镜像，社群反馈跑 uni-app 基座较常见。
  C. 继续折腾官方模拟器（换 android-28/29 的 x86/x86_64，或 -accel off 纯软件模拟）—— 收益低。

顺带得到的、可留用的结论
  1) 官方模拟器环境本身已经建好且可用：API 30 x86_64 这台（bilin_x86_64）客体稳定、
     硬件加速正常（WHPX）、adb / 截图 / logcat / adb reverse 链路都通。
     将来换真机或换第三方模拟器，这套 SDK 与 AVD 环境都可直接复用。
  2) §2.3 那 2 行 renderjs import 修复在任何 Android 设备上都是必需前提
     （App 端编译必须靠它才能过），与本次模拟器选型无关，建议无论如何先提交。
  3) 结论明确：App 端跑不通的原因**在 DCloud 基座与 x86 模拟器的兼容性**，
     不在比邻AI 的代码，也不是 renderjs 写法问题。
